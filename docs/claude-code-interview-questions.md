# Claude Code 面试题集

> 以下面试题按照初级 / 中级 / 高级三个维度设计，旨在考察候选人对 Claude Code（Anthropic AI Coding 工具）从**会使用**到**能设计**的完整理解链路。

---

## 初级：概念理解 + 基本使用

### 1. 概念题

**Claude Code 和普通 Claude 对话最大的区别是什么？它如何感知你的项目？**

**考察点：** 候选人对 Agent 态工具与普通 Chat 工具本质区别的理解深度。

**参考答案要点：**
- Claude Code 拥有**项目级上下文感知**能力（通过 `.claude/` 目录、文件系统读取、git 历史等），而非单轮对话
- 普通 Claude 是无状态的；Claude Code 通过**持久化会话**（会话文件、消息历史）维护跨轮次上下文
- Claude Code 内置了 **Tool Use**（Bash/Read/Edit/Grep/WebSearch 等），无需用户手动调用
- Claude Code 遵循 `.claude/commands/` 中的自定义命令和 `.claude/instructions/` 中的全局指令

---

### 2. 实操题

**给你一个陌生的项目，如何用 Claude Code 快速了解它的技术栈和代码结构？**

**考察点：** 实际动手能力 + 对工具能力边界的认知。

**参考答案要点：**
1. `ls` / `find` 查看目录结构和关键文件（package.json、requirements.txt、Cargo.toml 等）
2. 读取 `README.md`、`CLAUDE.md` 等文档了解项目意图
3. 用 `grep` 搜索关键关键词（如 `import`、`from`、`fn`、`def`）快速定位入口文件和核心模块
4. 查看 `.claude/` 目录了解已有的自定义规则和命令
5. 通过 `git log --oneline` / `git diff` 了解最近的变更脉络

---

### 3. 调试题

**Claude Code 连续回答了几次之后，开始答非所问，可能是什么原因？你会怎么排查？**

**考察点：** 调试思路 + 对 LLM 行为异常的系统性分析能力。

**参考答案要点：**
- **Token 溢出**：上下文窗口耗尽，早期对话内容被挤出。可通过减少上下文、手动 `clear` 或分 session 解决
- **系统指令漂移**（Instruction Drift）：模型逐渐偏离原始指令。可在对话中插入 `summary` 或重新发送 system prompt 纠正
- **角色/人格污染**：之前的对话内容干扰了当前任务。可用 `/clear` 重置会话
- **工具反馈误导**：某次工具调用返回了意外结果，导致后续推理基于错误前提
- **排查方法**：打开详细日志（`--verbose` 或 `.claude/settings.json` 中的日志配置），查看完整的 Agent 循环轨迹

## 中级：架构理解 + 问题解决

### 4. 架构分析

**Claude Code 的 Agent 循环（感知→规划→执行→反馈）是怎么实现的？如果要你简化成一个最小可用的 MVP，你会保留哪些模块？**

**考察点：** 对 Agent 系统架构的理解 + 抽象能力。

**参考答案要点：**

Agent 循环的核心步骤：
1. **感知（Perceive）**：读取用户输入 + 项目文件 + 会话历史，构建当前上下文
2. **规划（Plan）**：LLM 根据上下文决定下一步 action（读文件、执行命令、搜索、编辑等）
3. **执行（Act）**：调用对应工具，获取原始返回结果
4. **反馈（Observe）**：将工具执行结果注入下一轮 prompt，重新进入感知阶段

**MVP 保留模块：**
| 模块 | 保留理由 | 可删除/简化 |
|------|---------|-----------|
| REPL 交互层 | 用户输入/输出的唯一入口 | 不可删 |
| LLM 调用层 | Agent 决策核心 | 不可删 |
| 基础工具集（Read/Edit/Bash） | 执行能力的最小集合 | 不可删 |
| 会话管理 | 跨轮次上下文 | 可简化为单文件存储 |
| Skill 系统 | 扩展机制 | MVP 可删除 |
| MCP 协议 | 外部工具集成 | MVP 可删除 |
| 流式输出 | UX 优化 | 可简化为非流式 |

---

### 5. 场景设计

**如果 Claude Code 在每次 commit 前自动检查代码风格，需要几步？核心改动在哪？**

**考察点：** 基于现有架构做扩展设计的能力。

**参考答案要点：**
1. **注册 Git Hook**：在 `.git/hooks/pre-commit` 中调用 Claude Code CLI（或在 Claude Code 中内置 `pre-commit` 触发器）
2. **设计专用 Prompt**：告诉 Claude Code 扮演代码审查者，检查格式规范（ESLint、Prettier、Ruff 等）
3. **传入 diff 内容**：用 `git diff --cached` 获取 staged changes，注入到上下文中
4. **定义退出行为**：发现问题返回非零退出码阻止 commit；无问题则放行
5. **核心改动**：需要 Claude Code 支持**非交互式调用模式**（batch mode），接收参数直接输出结果，而非 REPL 循环

### 6. 性能 & 体验

**Claude Code 的 REPL 交互模式（实时输出、逐字显示）和普通 API 调用相比，在实现上有什么关键差异？**

**考察点：** 对流式通信（Streaming）实现原理的理解。

**参考答案要点：**
- **普通 API 调用**：等待完整响应后一次性返回（同步阻塞），用户感受到的是"等很久再看到结果"
- **REPL 流式输出**：服务端通过 **Server-Sent Events (SSE)** 或 **WebSocket** 逐 token 推送，客户端实时渲染，用户感受是"打字机效果"
- **实现差异**：
  - 服务端：需要支持流式响应（`stream: true`），边生成边返回
  - 客户端：非阻塞 I/O，接收到部分数据立即渲染，而非等待完整内容
  - 终端渲染：使用 ANSI 转义序列（如 `\r`、`\x1b[K`）在单行内原地更新
- Claude Code 使用的是 **Server-Sent Events**，通过 `/v1/messages` 接口的 `stream: true` 参数实现

**大文件 Token 溢出优化方案：**
- 读取文件时限制行数或使用语义分块（按函数/类分割）
- 对话中使用 `Compact` 操作，主动压缩历史上下文
- 对大文件分析任务拆分为多个小步骤（分章节阅读）

## 高级：系统设计 + 工程洞察

### 7. 系统设计

**如果要你给 Claude Code 添加"多 Agent 协作"功能（比如一个 Agent 写前端、一个写后端），你会怎么设计？会遇到什么一致性问题？**

**考察点：** 分布式 Agent 系统的设计能力。

**参考答案要点：**

**架构设计：**
```
User Intent
    │
    ▼
Orchestrator Agent（总控 Agent）
    ├── 任务拆解 → Frontend Agent（只读/修改前端代码）
    ├── 任务拆解 → Backend Agent（只读/修改后端代码）
    └── 协调同步 → Merge & Conflict Resolution
```

**核心组件：**
- **Orchestrator**：负责任务分解、分配、结果汇总
- **子 Agent**：各自有独立上下文（前端代码库子集 / 后端代码库子集）
- **通信总线**：子 Agent 间的消息传递（如后端 API 变更通知前端）
- **冲突解决层**：检测两个 Agent 对同一文件的修改，进行 merge 或人工仲裁

**一致性问题：**
- **文件竞争**：两个 Agent 同时修改同一文件 → 需要文件级锁机制
- **接口契约漂移**：后端改了 API 前端不知道 → 引入共享 schema（如 OpenAPI spec）
- **状态同步延迟**：一个 Agent 的输出是另一个 Agent 的输入，但两者执行有时间差 → 引入版本化的中间产物
- **目标对齐**：子 Agent 各自优化局部目标，可能与全局目标冲突 → 需要强约束的 system prompt

### 8. 工程哲学

**Claude Code 的 `instructions` 可以覆盖全局配置，这种"本地规则优先"的设计思路在工程上有什么好处和风险？**

**考察点：** 工程判断力 + 对配置/规则系统设计原则的理解。

**参考答案要点：**

**好处：**
- **精确性优先**：本地项目可能有特殊约定（如 Monorepo 中的路径规范、微服务的部署约束），本地规则比通用规则更准确
- **渐进式配置**：团队成员可以在不修改全局配置的情况下为特定项目定制行为
- **避免全局污染**：不会因为全局配置的变更而意外影响所有项目
- **符合 Git 的协作模型**：`instructions` 可以 commit 到 repo 中随代码一起版本化，新成员 clone 后自动继承项目规则

**风险：**
- **规则碎片化**：不同项目的 `.claude/instructions` 内容不一致，成员切换项目时需要重新适应
- **权限逃逸**：如果 Claude Code 的某些安全限制可以被 `instructions` 覆盖，可能产生安全风险（如禁止删除文件但被 override）
- **优先级冲突**：当全局规则和本地规则描述矛盾时，模型可能产生非预期行为
- **维护成本**：项目级规则容易过时（代码库演进但规则没更新），导致规则与实际行为脱节

**工程建议：**
- 关键安全类限制（如禁止执行 `rm -rf`）不应被本地规则覆盖
- `instructions` 内容应纳入 code review
- 定期用 `/compact` 或手动审查来验证规则是否仍然有效
